# D5.0.5 — Production QA, Recipient Isolation, Broadcast Audience & UI Hardening

## 1. Overview & Context

Following the release of D5.0.4, real-world testing on the production environment (`https://ivently.up.railway.app`) uncovered several behavioral and visual issues:
1. **Admin Test Pro Quota Toggle**: Admin observed "2 из 20" after toggling Pro access.
2. **Event Update Notification Delivery**: Users who clicked "Хочу пойти" (`EventInterest`) did not receive time/date change notifications when the organizer updated an event.
3. **Event Interest Broadcast Audience**: A broadcast targeted at "Хочу пойти" on an event with 2 interested users reached only 1 user.
4. **Broadcast Text Preview Overflow**: Medium/long texts and URLs in the composer preview expanded beyond the message bubble and modal container.
5. **My Events Segmented Control Overflow**: The 4-tab control ("Я иду", "Хочу пойти", "Подписки", "Прошедшие") exceeded the viewport width on mobile devices, causing horizontal page drag.
6. **Delete Event Confirmation Modal Position**: In the edit sheet, scrolling down to click "Удалить мероприятие" opened the confirmation modal attached high above the viewport due to CSS `transform` on the sheet container.
7. **City Selector Collision on Long Names**: Long city names like "Санкт-Петербург" clashed with the right viewport edge.

Release **D5.0.5** directly investigates the root causes of each issue, implements surgical fixes, verifies responsive frontend behavior, and provides complete automated regression coverage.

## 2. Root Cause Analysis & Technical Solutions

### 2.1 Issue 1: Pro Quota Persistence & Semantics
- **Root Cause**: Not a defect. Toggling the Pro plan (`POST /api/v1/admin/organizations/{id}/plan`) intentionally preserves broadcast history. If 2 marketing broadcasts were dispatched in the current calendar month, "2 из 20" is factually accurate.
- **Rules Enforced & Verified**:
  1. A newly activated Pro organization with no current-month marketing broadcasts begins at **0 used / 20 remaining**.
  2. Each valid, delivered marketing campaign decrements quota by 1.
  3. Disabling Pro test access preserves broadcast history in the database.
  4. Re-enabling Pro test access restores the exact current-month quota balance.
  5. Quota is never consumed by: Pro activation/deactivation, transactional notifications, event updates, event cancellations, or failed broadcasts with 0 delivered messages.
  6. Only broadcasts belonging to the specific organization in the current UTC month count.

### 2.2 Issue 2: Event Update Notification Recipient Isolation
- **Root Cause**: In D5.0.4, `notify_event_updated` queried only `EventAttendee` ("Я иду"). Users who clicked "Хочу пойти" (`EventInterest`) were completely omitted. Additionally, comparing `data.start_at` (offset-aware) with SQLite `event.start_at` (offset-naive) caused datetime comparison discrepancies.
- **Fix**:
  - In `backend/app/services/notification_service.py`: updated `notify_event_updated` to query both `EventAttendee` and `EventInterest`, deduplicating via `Set[int]`.
  - In `backend/app/services/event_service.py`: normalized timezone awareness before comparing `event.start_at` with `data.start_at`.
  - Confirmed that modifying non-operational fields (`title`, `description`, `category_id`, `price_amount`) or saving without changes triggers **zero** notifications.
  - Confirmed that passive viewers (`EventView`), organization subscribers without event relationship, and unrelated city users receive **zero** notifications.

### 2.3 Issue 3: Event Interest Broadcast Audience & Delivery
- **Root Cause**:
  - In `backend/app/services/broadcast_service.py`, `calculate_audience` applied a platform-wide 24h anti-fatigue query without scoping by `Broadcast.organization_id == organization_id`. If a test user had received any marketing broadcast across the platform within 24h, they were stripped from `eligible_user_ids`.
  - For `EVENT_INTEREST`, anti-fatigue should only apply if the user received a broadcast for *that specific event* within 24h, not across different events or organizations.
  - In `frontend/src/components/OrganizerWorkspace.tsx`, step 2 displayed raw `selectedEvent.interest_count` rather than `previewData.eligible_recipients`, misleading organizers when audience calculations differed from raw clicks.
- **Fix**:
  - Scoped anti-fatigue queries strictly to `Broadcast.organization_id == organization_id`.
  - For `target_type == EVENT_INTEREST`, scoped anti-fatigue to the specific `event_id`.
  - Implemented distinct user ID extraction on `EventInterest` joined with `User.telegram_id.isnot(None)`.
  - Updated recipient insertion in `create_broadcast` to deduplicate user IDs (`added_uids`).
  - Updated UI in `OrganizerWorkspace.tsx` to display `previewData.eligible_recipients` with total segment comparison.

### 2.4 Issue 4: Broadcast Text Preview Word Wrapping
- **Root Cause**: In `frontend/src/components/OrganizerWorkspace.tsx`, the message preview bubble had `whitespace-pre-wrap` but lacked `break-words [overflow-wrap:anywhere] max-w-full`. Long words and URLs forced the bubble and modal to expand horizontally.
- **Fix**: Added `break-words [overflow-wrap:anywhere] max-w-full` and `overflow-hidden` to the preview bubble container, mimicking native Telegram chat bubble wrapping.

### 2.5 Issue 5: My Events Segment Control Overflow
- **Root Cause**: In `frontend/src/components/OrganizerTab.tsx`, `AnimatedSegmentedControl` was called with `equalWidth={false}` and `scrollable={false}`. Four tabs with `min-w-fit px-3 whitespace-nowrap` plus zero count badges (`0`) required ~395px, exceeding 320px–390px mobile viewports and causing page-level horizontal drag.
- **Fix**:
  - In `AnimatedSegmentedControl.tsx`: refined `size="sm"` with compact padding (`px-0.5 xs:px-1`), smaller font (`text-[10.5px] xs:text-[11px]`), and rendered count badges **only when count > 0** (saving ~80px of wasted zeros).
  - In `OrganizerTab.tsx`: set `equalWidth={true}` with an `overflow-hidden w-full` containment wrapper.
  - Guaranteed horizontal page lock (`overflow-x-hidden`) across 320px, 360px, 390px, and 430px viewports.

### 2.6 Issue 6: Delete Event Confirmation Modal Position
- **Root Cause**: In `CreateEventModal.tsx`, the confirmation modal `showDeleteConfirm` was rendered as a child of the form container which had `.sheet-slide-up` (CSS `transform`) and `overflow-y-auto`. Per CSS specification, any ancestor with `transform` creates a local containing block for `position: fixed` elements, anchoring the modal to the top of the scrolled sheet rather than the viewport.
- **Fix**: Portaled `showDeleteConfirm` to `document.body` via React's `createPortal(..., document.body)` with `fixed inset-0 z-[100]`. It is now 100% viewport-centered regardless of where the user is scrolled in the form.

### 2.7 Issue 7: City Selector Long Names Truncation
- **Root Cause**: In `frontend/src/components/Header.tsx`, city name `span` was set to a static `max-w-[120px]` and parent containers lacked flex constraints (`min-w-0`), pushing past the viewport edge on narrow screens with names like "Санкт-Петербург".
- **Fix**: Applied responsive max-width (`max-w-[85px] xs:max-w-[110px] sm:max-w-[140px] truncate text-ellipsis`), `min-w-0` on button and container, and accessible `title={currentCity ? currentCity.name : 'Выбрать город'}`.

## 6. Known Limitations & Scope Boundaries

1. **In-Process Delivery**: Broadcast dispatch continues to run asynchronously in-process. At 100k+ scale, external Redis/PostgreSQL queue workers (ARQ/Celery) will be required.
2. **Global Telegram Rate Limit**: Telegram Bot API enforces a global cap of 30 messages/second. The application rate limiter is calibrated to 25 msg/sec to prevent HTTP 429 throttling.
