# Ivently — D5.0 Pro Foundation & Entitlement Engine

> **Статус документа:** Архитектурная документация фундамента Pro и системы прав (Approved Architecture Reference)  
> **Версия:** 1.0.0  
> **Спринт:** D5.0  
> **Базовый коммит:** `3b5216b`  
> **Принцип:** Никаких платежных провайдеров и фальшивых биллингов в кодовой базе. Backend — единый source of truth для всех планов и прав.

---

## 1. Why (Зачем нужен D5.0)

В спринтах D1.0–D4.3 в Ivently был выстроен и верифицирован в продакшене полный цикл работы организатора: создание событий, модерация, сбор откликов («Я иду» / «Хочу пойти»), накопление базы подписчиков, проведение Telegram-рассылок и аналитика вовлеченности.

Цель этапа **D5.0** — создать масштабируемый фундамент для платных возможностей организатора (**Ivently Pro**), не подключая пока реальные платежные шлюзы и не ломая существующие бесплатные сценарии.

Вместо разбросанных проверок вида `if plan == "pro"` по десяткам контроллеров и компонентов, D5.0 внедряет:
- Централизованный движок прав (**Entitlement Engine**).
- Единый реестр возможностей (**Capability Registry**) со статусами `available`, `locked`, `coming_soon`.
- Защиту изоляции организаций (**Multi-Org Isolation**): тариф принадлежит организации, а не пользователю целиком.
- Серверный контроль квот (**Backend Enforcement**) через `require_entitlement(...)`.
- Прозрачный интерфейс раннего интереса (**Fake Door UX**) без обмана пользователей, без запроса банковских карт и без фальшивых платежных экранов.

## 2. Current Architecture (Текущая архитектура)

```
Plan
  ↓
Entitlements
  ↓
Capability checks
  ↓
Backend enforcement
  ↓
Frontend UI state
```

- **Backend является Source of Truth:** Фронтенд никогда не решает самостоятельно, доступна ли функция организатору. Фронтенд получает декларативный снимок прав и квот через `GET /api/v1/organizer/entitlements`.
- **Защита бесплатного ядра (Protected Free Core):**
  - Публикация событий, приём регистраций, профили организаций, сбор подписчиков и базовые рассылки остаются бесплатными.
  - Бесплатный тариф имеет гарантированную ежемесячную квоту рассылок (`settings.FREE_BROADCASTS_PER_MONTH`, по умолчанию 3 рассылки в месяц).

## 3. Plan Model (Модель тарифов)

В D5.0 поддерживаются строго два тарифа:
1. **`FREE` (Базовый бесплатный тариф):**
   - Назначается по умолчанию любой создаваемой организации.
   - Базовые рассылки по органическим подписчикам в пределах бесплатной квоты.
   - Полный доступ к базовой аналитике, событиям и аудитории.
2. **`PRO` (Профессиональный тариф для площадок):**
   - Расширенный лимит рассылок (`settings.PRO_BROADCASTS_PER_MONTH`, по умолчанию 30 в месяц).
   - Углубленная аналитика аудитории и событий.
   - Дополнительные инструменты работы с лояльной аудиторией.

> **Статусы тарифа (`PlanStatus`):**
> - `active` — план активен.
> - `expired` — срок действия истек; система автоматически деградирует организацию до `FREE`.
> - `cancelled` — план отключен; организация обслуживается по правилам `FREE`.

## 4. Entitlement Model & Multi-Organization Isolation

### 4.1. Сущность `OrganizationPlan` (`organization_plans`)

```python
class OrganizationPlan(Base):
    __tablename__ = "organization_plans"

    id = Column(String(36), primary_key=True)
    organization_id = Column(String(36), ForeignKey("organizations.id", ondelete="CASCADE"), unique=True, index=True)
    plan = Column(String(20), nullable=False, default="free")
    status = Column(String(20), nullable=False, default="active")
    starts_at = Column(DateTime(timezone=True), nullable=False)
    expires_at = Column(DateTime(timezone=True), nullable=True)
    created_at = Column(DateTime(timezone=True), nullable=False)
    updated_at = Column(DateTime(timezone=True), nullable=False)
```

### 4.2. Изоляция организаций (Multi-Organization Isolation)
Один пользователь может владеть несколькими независимыми организациями:
- **Организация А (Концертный зал):** подключен тариф Pro (увеличенный лимит рассылок, глубокая аналитика).
- **Организация Б (Уютное кафе):** работает на базовом тарифе Free.

Тариф привязан к `organization_id`. Доступ к правам Организации А никак не наделяет правами Организацию Б, даже если у них один и тот же владелец.

## 5. Capability Registry (Реестр возможностей)

Все возможности платформы регистрируются в едином реестре `CAPABILITY_REGISTRY` в `app/services/entitlement_service.py`:

| Capability Key | Название | Free | Pro | Статус реализации |
| :--- | :--- | :--- | :--- | :--- |
| `broadcasts_extended` | Расширенные рассылки | locked (при исчерпании квоты) | available | Реализовано в D5.0 |
| `audience_advanced` | Глубокая аналитика аудитории | locked | available | Заложено в D5.0 |
| `analytics_advanced` | Расширенная аналитика событий | locked | available | Заложено в D5.0 |
| `reminders` | Авто-напоминания о событиях | coming_soon | coming_soon | Запланировано |
| `audience_segments` | Сегментация аудитории | coming_soon | coming_soon | Запланировано |
| `export` | Экспорт списков и CRM | coming_soon | coming_soon | Запланировано |
| `organization_verification`| Верификация организации | coming_soon | coming_soon | Запланировано |
| `priority_placement` | Приоритетное размещение | coming_soon | coming_soon | Запланировано |

## 7. What is Implemented in D5.0 (Что реально сделано)

1. **Модель `OrganizationPlan`:** персистентное хранение тарифа, дат начала/окончания и статуса.
2. **Центральный `EntitlementService`:**
   - Резолвер тарифа с автоматической деградацией при истечении срока (`expires_at < now()`).
   - Метод `require_entitlement(...)` для валидации возможностей.
   - Метод `enforce_broadcast_capacity(...)` для контроля ежемесячных лимитов.
   - Конфигурируемые лимиты в `settings` (`FREE_BROADCASTS_PER_MONTH`, `PRO_BROADCASTS_PER_MONTH`).
3. **API эндпоинты:**
   - `GET /api/v1/organizer/entitlements` (проверка прав и квот с проверкой владения организацией).
   - `GET /api/v1/admin/organizations/{org_id}/entitlements` (инспекция для администраторов).
   - `POST /api/v1/admin/organizations/{org_id}/plan` (ручное управление тарифом для тестов и разработки).
4. **Backend Enforcement:**
   - Проверка лимитов в `create_broadcast`. Бесплатные рассылки до лимита проходят беспрепятственно; при превышении возвращается `HTTP 403 Forbidden` с кодом `ENTITLEMENT_REQUIRED`.
5. **Frontend Fake Door UX:**
   - Информационная плашка «Pro для организаторов» в кабинете организатора.
   - Модальное окно «Pro — скоро» со списком планируемых возможностей.
   - Текст: *«Оплата пока недоступна. Мы готовим Pro. Все базовые функции Ivently остаются бесплатными для организаторов.»*
   - Никаких форм ввода карт, фальшивых цен и фиктивных платежных переходов.
6. **База данных и миграции:**
   - Идемпотентная миграция таблицы `organization_plans` и индекса `idx_organization_plans_org_status` в `database.py`.

## 8. What is Intentionally NOT Implemented (Что намеренно НЕ сделано)

- **Payment integration intentionally deferred.**
- НЕ подключены банковские эквайринги (ЮKassa, CloudPayments, Tinkoff, Stripe).
- НЕ подключены Telegram Stars.
- НЕТ таблиц счетов, инвойсов, чеков и платежных транзакций.
- НЕТ автосписаний и рекуррентных подписок.
- НЕТ экранов запроса банковских карт.
- НЕТ фиктивных маркетинговых заявлений об окупаемости или конверсиях («Pro увеличит продажи на 300%»).

## 9. Future Payment Integration Point (Точка интеграции платежей)

Когда продукт и юридическая база будут готовы к приёму платежей (D5.1+):
1. Платёжный провайдер подключается как изолированный вебхук-сервис:
   `POST /api/v1/webhooks/payments/{provider}`
2. При подтверждении успешного платежа платёжный сервис вызывает:
   `await EntitlementService.set_organization_plan(session, organization_id, plan="pro", expires_at=new_expiration)`
3. Ядро приложения, авторизация и логика проверки прав остаются на 100% неизменными.

---

## 10. Multi-Organization Considerations

- Каждый вызов `GET /api/v1/organizer/entitlements` принимает параметр `org_id`.
- Проверяется принадлежность организации текущему пользователю (`owner_user_id == current_user.id`). Попытка запросить права чужой организации блокируется с `HTTP 403 Forbidden`.
- Удалённая организация (`status == "deleted"`) возвращает `HTTP 404 Not Found`.

## 11. Testing & Verification

Покрытие тестами в `tests/test_pro_entitlements.py`:
1. `test_new_organization_resolves_to_free`: новая организация всегда на Free.
2. `test_free_capability_resolution`: правильные статусы `locked` и `coming_soon`.
3. `test_pro_capability_resolution`: статус `available` для Pro-функций.
4. `test_unknown_capability_handled_safely`: безопасная обработка несуществующих фичей.
5. `test_expired_entitlement_degrades_to_free`: автоматическая деградация при истечении срока.
6. `test_multi_organization_isolation`: независимость тарифов у одного владельца.
7. `test_deleted_organization_returns_404`: удаленная организация не отдает права.
8. `test_non_owner_cannot_access_entitlements`: чужой пользователь получает 403 Forbidden.
9. `test_frontend_endpoint_data_safety`: отсутствие утечек `telegram_id` и секретов.
10. `test_free_user_quota_enforcement`: блокировка рассылок при исчерпании бесплатной квоты.
11. `test_existing_free_broadcast_flow_works`: штатная работа рассылок в пределах бесплатной квоты.
12. `test_pro_broadcast_quota_allowed`: успешная отправка рассылок в Pro-тарифе с увеличенным лимитом.
13. `test_migration_fresh_and_idempotent`: безопасность и идемпотентность миграций `init_db`.
