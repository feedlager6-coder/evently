# D5.0.4 — Event Lifecycle, Telegram Notifications, Broadcast Idempotency & Pro Quota Hardening

## 1. Overview & Context

In Ivently D5.0.3, admin testing capabilities and UX copy cleansing were completed. In D5.0.4, we address operational integrity, delivery reliability, strict recipient isolation for transactional notifications, broadcast delivery idempotency, and commercial Pro quota alignment.

Key objectives:
1. **Telegram Send Photo Timeout & Fallback Fix**: Eliminate duplicate message delivery caused by fallbacks on network/timeout errors.
2. **Broadcast Delivery Idempotency**: Atomic recipient-level status locking (`PENDING` -> `SENDING` -> `SENT`/`FAILED`).
3. **Operational Event Notification Recipient Isolation**:
   - Event Date/Time or Venue change -> ONLY confirmed attendees (`EventAttendee` / "Я иду").
   - Event Cancellation -> Confirmed attendees (`EventAttendee`) + interested users (`EventInterest` / "Хочу пойти"), deduplicated.
   - Zero notifications sent to general organization subscribers, non-interested viewers, or city blasts.
   - Zero marketing quota consumption; zero marketing attribution tokens.
4. **Organizer Event Editing Flow**:
   - Replaced standalone "Удалить мероприятие" in `EventDetailsModal` with "Редактировать событие" opening `CreateEventModal` in edit mode (`initialEvent`).
   - Destructive event deletion safely relocated inside edit flow with confirmation modal.
5. **Personal Events Hub Lifecycle**:
   - Separated into Active (`start_at >= now`) and History ("Прошедшие", `start_at < now`).
   - City switching preserves all user relationships (RSVPs, Interests, Subscriptions).
6. **Pro Quota Hardening**:
   - Quota set to **20 broadcasts per month**.
   - Newly activated Pro organizations start at 0/20 used (20 remaining).
   - Only created, completed/queued marketing campaigns consume quota (failed with 0 sent, cancelled, transactional, and other organizations do not count).

## 2. Technical Architecture & Implementation

### 2.1 Broadcast Delivery Idempotency & Safe Photo Fallback
- **Problem**: When `sendPhoto` encountered a `httpx.TimeoutException` or socket timeout, Telegram may have already received and scheduled the photo for delivery. Falling back to `sendMessage` caused users to receive both the photo and a redundant text message. Furthermore, concurrent or repeated dispatch could process the same recipient multiple times.
- **Solution**:
  - In `app/services/broadcast_service.py` and `app/services/notification_service.py`:
    - Strict exception differentiation: `httpx.TimeoutException` and `httpx.NetworkError` during `sendPhoto` are logged as delivery failures without fallback.
    - Fallback to text message `sendMessage` is ONLY triggered on deterministic HTTP 400 client errors (e.g. invalid photo URL, unsupported image format).
  - In `app/services/broadcast_service.py`:
    - Atomic per-recipient status check: only recipients with `status == RecipientStatus.PENDING` are processed.
    - Immediate atomic transition to `RecipientStatus.SENDING` committed to the database before network dispatch.
    - Post-send transition to `RecipientStatus.SENT` or `RecipientStatus.FAILED` with Telegram `message_id` or error details recorded.

### 2.2 Transactional Recipient Isolation Rules

| Event Action | Target Audience | Excluded Audiences | Quota Impact | Attribution Tokens |
|:---|:---|:---|:---|:---|
| **Date/Time Changed** | Confirmed Attendees (`EventAttendee`) | Interested, Org Subscribers, City feed | 0 (Free) | None |
| **Venue/Address Changed**| Confirmed Attendees (`EventAttendee`) | Interested, Org Subscribers, City feed | 0 (Free) | None |
| **Event Cancelled** | Attendees + Interested (`EventAttendee` ∪ `EventInterest`) | Org Subscribers, City feed | 0 (Free) | None |
| **Marketing Broadcast** | Org Subscribers or Event Interest | Public / Unsubscribed | 1 / campaign | Attached (`?b_ref=...`) |

Transactional notifications are system-generated and cannot be triggered or customized by organizers as marketing broadcasts.

### 2.3 Organizer Event Management Flow
- `EventDetailsModal`:
  - Removed top-level delete button.
  - Added primary "Редактировать событие" action button for organizers/owners/admins.
- `CreateEventModal`:
  - Enhanced to support `initialEvent` prop for updating existing events.
  - PATCH request to `/api/v1/events/{id}` supporting `title`, `description`, `category_id`, `city_id`, `start_at`, `venue_name`, `address`.
  - Added "Удалить событие" button inside edit view with confirmation modal.
- `PersonalHub` / `OrganizerTab`:
  - Added segment tab for past events ("Прошедшие").
  - Filter rule: `event.start_at < now` classifies an event as past history without purging or modifying database records.

### 2.4 Pro Quota Semantics
- `PRO_BROADCASTS_PER_MONTH: int = 20` defined in `app/config.py`.
- `EntitlementService.get_monthly_broadcast_usage`:
  - Filters strictly for `broadcast_type == 'marketing'`.
  - Filters for status in `[COMPLETED, PROCESSING, QUEUED, PARTIALLY_FAILED]`.
  - Excludes `CANCELLED` and `FAILED` broadcasts where `sent_count == 0`.
  - Strictly scoped to the specified `organization_id` and the current UTC calendar month.

## 3. High-Scale Architecture Audit (100,000+ Users)

To scale broadcast and notification delivery to 100k+ users reliably without hitting Telegram Bot API rate limits (30 messages/second global limit) or exhausting database connection pools:

1. **Queueing & Worker Decoupling**:
   - Transition from FastAPI in-process background tasks to a dedicated persistent worker tier (e.g. Celery / ARQ with Redis, or PostgreSQL `pgmq`/`SKIP LOCKED` job queue).
   - Prevents web process worker starvation and enables graceful resumption after deploy or process crash.
2. **Rate Limiting & Token Bucket Dispatch**:
   - Implement a distributed token bucket or sliding-window rate limiter constrained to 25–28 messages/second across all worker nodes to stay safely beneath Telegram's 30 msg/sec ceiling.
   - Per-chat concurrency limits (max 1 message/sec per recipient chat).
3. **Database Streaming & Bulk Recipient Ingestion**:
   - Stream recipient queries using cursor pagination (`yield_per(1000)`) instead of loading all 100k IDs into memory.
   - Bulk insert `broadcast_recipients` in chunks of 5,000 using PostgreSQL `COPY` or multi-value `INSERT`.
4. **Resumable Batches & Failure Isolation**:
   - Idempotent recipient status tracking (`PENDING` -> `SENDING` -> `SENT`/`FAILED`) ensures any interrupted broadcast can be resumed from the exact failure point without duplicate messages.
   - Exponential backoff with jitter on Telegram HTTP 429 (`retry_after`).
